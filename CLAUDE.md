# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Excel on a Stick** (`mod.id = excelcomputer`, named Excel Computer before; the id, package and `excelcomputer` folders keep the old name so existing worlds and workbooks still load): a Minecraft mod that opens `.xlsx` / `.csv` workbooks in an in-game spreadsheet screen, using Apache POI. It is one source tree built for many Minecraft versions and loaders with [Stonecutter](https://stonecutter.kikugie.dev/wiki/start/) (forked from the Stonecutter Fabric & NeoForge template).

Targets (declared in `settings.gradle.kts`): `1.20.1` (fabric, forge), `1.21.1`, `1.21.10`, `26.1.2`, `26.2` (fabric, neoforge). Folders under `versions/` that are not in `settings.gradle.kts` (e.g. `1.21.11-*`, `26.3-*`) are leftovers and are not built.

## Commands

Use `./gradlew` (Git Bash) or `gradlew.bat` (PowerShell). Subprojects are named `{mcVersion}-{loader}`.

**Gradle itself must run on Java 25** (Loom 1.18 requires it). `gradle/gradle-daemon-jvm.properties` (`toolchainVersion=25`) makes Gradle pick an installed JDK 25 by itself, so the default Java 21 `JAVA_HOME` and IntelliJ's Gradle JVM no longer matter.

- Build one target: `./gradlew :1.21.10-fabric:build`
- Build every target and copy jars to `build/libs/{mod.version}/`: `./gradlew buildAndCollect` (or `:<project>:buildAndCollect`)
- Run the client: `./gradlew :1.21.10-fabric:runClient` (dev server: `runServer`). Run dirs are `run/{project}` and `run/{project}-server`.
- Switch the active version (rewrites the `//?` comments in `src/` for that target): `./gradlew "Set active project to 1.21.1-neoforge"`, or reset to the VCS version with `./gradlew "Reset active project"`. Do this before editing code for a specific target in the IDE.

There are no tests and no linter. "Verifying" a change means compiling the affected targets, ideally both loaders and the oldest and newest versions it touches.

## Stonecutter: how version/loader differences work

- **Only one copy of the code exists**, in `src/main`. Differences between versions and loaders are written as Stonecutter comments:
  ```java
  //? if >=1.21 {
  return ResourceLocation.fromNamespaceAndPath(MOD_ID, path);
  //?} else {
  /*return new ResourceLocation(MOD_ID, path);
  *///?}
  ```
  Branches that are not active are commented out with `/* ... */`. When you add a branch, comment out the inactive one in the same style. Loader constants: `fabric`, `neoforge`, `forge` (from `stonecutter.gradle.kts`).
- **Committed source must stay in the `vcsVersion` state (`1.21.10-fabric`)**, which is also `stonecutter active` in `stonecutter.gradle.kts`. If you switched the active project, reset it before committing.
- `stonecutter.gradle.kts` also does automatic text replacements: `ResourceLocation` → `Identifier` on >=1.21.11, and on >=26.1 `GuiGraphics` → `GuiGraphicsExtractor`, `graphics.drawString`/`drawCenteredString` → `text`/`centeredText`, `super.render(` → `super.extractRenderState(`, `net.minecraft.Util` → `net.minecraft.util.Util`, Fabric `ItemGroupEvents` → `CreativeModeTabEvents`, and on >=26.2 `minecraft.setScreen(` → `minecraft.gui.setScreen(`. Write the old names in source. **Replacements are reversible**: they also run backwards for older targets, so a pattern must be specific enough that its *replacement* text never appears elsewhere (a bare `.text(` → `.drawString(` once broke `change.text()` on <26.1).
- Signature changes can't be expressed as replacements and use `//? if >=26.1` blocks instead: `Screen.render` → `extractRenderState` overrides, and `Screen.resize(Minecraft,int,int)` → `resize(int,int)`.
- Per-version/loader properties (loader versions, Fabric API, compat ranges, `mod.version`) are in `stonecutter.properties.toml`, in tables keyed `["<mc>"]` and `[<loader>."<mc>"]`. `gradle.properties` holds only Gradle JVM options.

## Build scripts (one per loader)

Each version node uses `build.{loader}.gradle.kts`:

- `build.fabric.gradle.kts`: Fabric Loom via `dev.kikugie.loom-back-compat` (handles obfuscated and 26.1+ unobfuscated Minecraft). POI is bundled as jar-in-jar (`include`).
- `build.neoforge.gradle.kts`: ModDevGradle plus Shadow. POI is shaded, and commons-collections4/math3/compress, SparseBitSet and curvesapi are **relocated** to `io.github.reverendbrown.excelcomputer.libs.*` because NeoForge refuses duplicate packages from other mods (e.g. Iris). POI, xmlbeans and the OOXML schema packages cannot be relocated: xmlbeans finds schema classes by names stored in its binary `.xsb` files. The shadow jar is the real mod jar; the plain jar has the `slim` classifier.
- `build.forge.gradle.kts`: ModDevGradle legacyforge for 1.20.1, also shaded.
- **Mixins** (`mixin/`, `excelcomputer.mixins.json`, the same config on every target) are for shared workbook map pictures (`share/SheetPreview`, `share/PreviewMaps`). `ItemInHandRendererMixin` swaps a held picture's paper border for `share/WindowFrame` on all versions. On 1.20.1 only, it and `ItemFrameMixin` also make the item draw as a map at all; 1.21+ vanilla draws any `MapItem` with a map id, so `ItemFrameMixin` is empty there. Fabric lists the config in `fabric.mod.json`, NeoForge in `neoforge.mods.toml` (`[[mixins]]`); both strip the `refmap` line (Loom remaps statically, NeoForge runs with Mojang names). Forge uses MDG's `mixin {}` block, the `MixinConfigs` manifest entry, and a refmap added to the shadow jar. Gradle doesn't count `filter {}` code as a task input, so after editing one, run `processResources --rerun` or `clean`.
- `buildSrc/neoforge-mutex`: limits `createMinecraftArtifacts` to one run at a time across versions.

Library version constraints (comments in the build scripts explain why; keep them when editing):
- POI is **5.2.5** on >=1.21 and **5.2.3** (xmlbeans 5.1.1) on 1.20.1. Newer POI needs a newer commons-io than Minecraft ships and crashes with `NoSuchMethodError` outside dev.
- log4j, commons-io and commons-codec are excluded because Minecraft provides them.
- `poi-ooxml-full` is used instead of `poi-ooxml-lite` (the lite jar lacks the autofilter/table XML classes).
- The Word/PowerPoint/Visio/signature parts of POI are left out of the jar (~5 MB). The folders are listed in `gradle/poi-trim.txt`; `buildSrc/src/main/kotlin/PoiTrim.kt` turns them into shadowJar excludes (NeoForge/Forge) and rewrites the nested `poi-ooxml` jars after the mod jar is built (Fabric; Loom only nests Maven artifacts). `org/apache/poi/xwpf` must stay: opening any workbook touches `XWPFRelation`. Test any change to the list by opening, recalculating and saving real workbooks against the built jar.
- Guide pictures are 640x360 (or 960x540 for spreadsheet shots) 256-color PNGs; full-color screenshots cost ~5x the space.
- On NeoForge, transitive deps are off, so every needed library is listed explicitly at the version POI declares (e.g. commons-compress 1.25.0).

Resources are shared too. `processResources` in each script handles the differences:
- Only that loader's metadata is kept (`fabric.mod.json`, `META-INF/neoforge.mods.toml`, `META-INF/mods.toml` + `pack.mcmeta` for Forge). The rest are excluded, and `${...}` placeholders are expanded from the properties.
- Recipes are written in the 1.21.2+ format and rewritten by regex for <1.21.2 (ingredient objects) and <1.21 (`item` result key, plural `recipes/` / `loot_tables/` folders).

## Code architecture (`src/main/java/io/github/reverendbrown/excelcomputer`)

- **Entry points per loader**: `ExcelComputerFabric` / `ExcelComputerNeoForge` / `ExcelComputerForge` (common init) and the matching `*Client` classes. Each file is wrapped entirely in `//? if <loader>`. Fabric registers directly in `ModBlocks`/`ModItems.initialize()`. NeoForge/Forge register the same static instances inside `RegisterEvent` and add them to creative tabs through events.
- **Client/server split**: the block (`block/ExcelComputerBlock`) and item (`item/ExcelOnAStickItem`) run on both sides, so they must not reference client classes. They call `ClientHooks.openWorkbookPicker`, a `Runnable` that only the client entry point fills in. A dedicated server never loads screens; it only uses POI for Redstone Connectors.
- **Flow**: `WorkbookPickerScreen` lists files from `WorkbookFiles` (`<gameDir>/excelcomputer/workbooks`, `.xlsx` and `.csv`) and opens a `SpreadsheetScreen`.
- `SpreadsheetScreen` (~3700 lines) handles all rendering and input: grid, ribbon tabs (Home/Insert/Draw, laid out in labelled groups), formula bar with the fx button, sheet bar (tabs + column scroll bar, drawn by the screen itself), selection, zoom, resizing, plus the `FormatMenu`, `FilterMenu`, `BorderMenu` and `FunctionMenu` popups. Tables can be sorted by a column (`sortTable`: the filter dropdown's top rows, the right-click menu, Insert > Sort & Search; whole rows move as chained cell edits plus a `TableChange` for filter-hidden rows, so it is one undo step) and searched (`TableSearchBar`, Ctrl+F: view-only, `searchHides` makes non-matching rows 0 tall and `rowHidden` skips them when moving; nothing is written to the file). It holds most of the `//? if >=1.21.6` / `>=1.21.9` rendering and input API branches. Opening and saving run on a single background thread (`WORKBOOK_IO`); `tick()` picks up the result, and input is ignored while a save runs because POI workbooks are not thread-safe.
- `WorkbookManager` wraps the POI `Workbook`: cell read/write, formula evaluation (`recalculate`), styles (`CellFormat`, deduplicated through `derivedStyles`), tables/autofilters (`TableInfo`, with raw `CT*` XML beans), column/row sizes, and atomic `save`. It uses only POI and plain Java (no Minecraft classes), so it can be compiled and tested outside the game against a given set of library jars. It has a **CSV mode** (`workbook == null`, `csvRows` instead), so check `csvMode` when adding features.
- `ViewStateStore` saves zoom and scroll position per workbook in `view-state.properties` next to the workbooks folder. It never writes to the workbook files.
- **Redstone Connector** (`redstone/`): **Hidden for now**: `ExcelComputer.REDSTONE_CONNECTOR = false` keeps its block and item from being created or registered, and the build scripts read that line to leave out its resources. Run `clean` before a release build, because stale copies can linger in `build/resources`. a block that runs a workbook on the server. Right-clicking it holding Excel on a Stick opens `WorkbookPickerScreen(pos)` in link mode; the chosen .xlsx is uploaded (`CONNECTOR_UPLOAD_BEGIN` + the usual chunks), `RedstoneSheet.ensure` adds a `Redstone` sheet (Side / In / Out, rows N, S, E, W, Up, Down), and the copy is stored in `<world>/excelcomputer/connectors/<id>.xlsx`, keyed by dimension and position in `links.properties` (no block entity). Right-clicking otherwise downloads that copy (`CONNECTOR_OPEN`) into a `SpreadsheetScreen` whose saves upload it back. `RedstoneConnectors.update` runs on a scheduled block tick after a neighbor change: it writes the incoming signals into In, recalculates with POI, and reads Out (0-15, TRUE = 15) as weak power per side.
- **Linked blocks** (`link/LinkedWorkbooks`): the link/upload/download/storage code shared by the Redstone Connector and the Logistics Hubs, with one instance per block kind (`RedstoneConnectors.LINKED`, `LogisticsHubs.LINKED`). Each kind keeps a `<world>/excelcomputer/<folder>/` with the copies and its `links.properties`. The `CONNECTOR_*` messages carry only a position, and `ShareServer` dispatches through `LinkedWorkbooks.at` based on the block found there. On the client, `ShareClient.linkedLabel(pos)` names the block for UI text.
- **Logistics Hubs** (`logistics/`): four tier blocks (`HubTier`: range, items per cycle, cycle ticks, max inventories, other dimensions on Netherite), all `LogisticsHubBlock`, registered from `ModBlocks.LOGISTICS_HUBS`. Hub Upgrades (`item/HubUpgradeItem`, `ModItems.HUB_UPGRADES`: iron, diamond, netherite) turn the hub one tier below into theirs in place via `LogisticsHubs.upgrade`; `LogisticsHubBlock.upgrading` stops the block swap from deleting the link, and `HubDirectory.retiered` fixes the tier in players' hub lists. Hubs never take an uploaded file: the first time someone opens a hub, the server makes its workbook from a template (`LinkedWorkbooks.Template`: the `Inventories`, `Stock` and `Transfers` sheets from `LogisticsSheets`), and later saves are checked against `LinkedWorkbooks.Limits` (file size, unpacked size, filled cells, formulas). The player who places a hub owns it (`HubDirectory`, `hubs/owners.txt`). Only the owner and the members they add in the picker's Access panel (`HUB_MEMBER_ADD` / `HUB_MEMBER_REMOVE`, online players only, `hubs/members.txt`) may open, save or choose the hub or register inventories to it (`HubDirectory.mayUse`, plugged into `LinkedWorkbooks.access`); only the owner renames, manages members or mines it (`LogisticsHubBlock.getDestroyProgress`). Any linked block's workbook is edited by one player at a time: `LinkedWorkbooks.editors` is taken on download or save, and released by `CONNECTOR_CLOSE` (sent when the `SpreadsheetScreen` or the loading screen closes), or when the holder is offline; an owner may have at most `maxHubsPerPlayer` hubs with a workbook, and only the owner can rename. Cycles share a per-tick time budget, run oldest-waiting first, catch up on items after waiting (`hubCatchUpCycles`), and a hub whose cycle is too slow is paused. The limits are in `ServerConfig` (`config/excelcomputer-server.properties`, read when a world starts). Right-clicking a hub adds it to that player's list of hubs and makes it their active one; `HubDirectory` keeps these lists and the hub names (`hubs/known.txt`, `hubs/names.txt`). A player can open and save any hub on their list from anywhere: `LinkedWorkbooks.resolve` drops the reach check via `HubDirectory.levelOfKnown`. The client gets the list through `HUB_QUERY` / `HUB_LIST` (`ShareClient.knownHubs`). The picker's hub row has a dropdown (choose the active hub, or forget one with `HUB_CHOOSE` / `HUB_FORGET`) plus Open and Rename (`HUB_RENAME`; names are per hub, shared by every player). Sneak-using the stick in the air opens the active hub. Sneak-right-clicking a block with the stick (`ExcelOnAStickItem.useOn`) adds or removes that block face, which is stored in `hubs/inventories.txt`; only registered inventories are used. Each cycle is a self-rescheduling block tick (`LogisticsHubs.cycle`). It counts the items, writes Stock (with the named ranges `StockInventory` / `StockItem` / `StockCount`), recalculates, then runs each Transfers row (From, To, Item filter via `ItemFilter`, Amount), and skips the cycle when nothing has changed. The Inventories sheet's Name and Side columns are editable, and deleting or clearing a row then saving unregisters that inventory (`LogisticsHubs.applySavedInventories`, run from `LinkedWorkbooks.onSaved` only on a player's save, never for a fresh template, and only for inventories registered before that player's download, recorded by `onSent`). The Inventories headers and notes are rewritten every full cycle (`LogisticsSheets.writeGuide`), so older hubs get the current text. Rows map to inventories by position (`matchRows`). Side takes Top/Bottom/North/South/East/West or Input/Fuel/Output. Items go in only through that side; taking items out tries that side, then the bottom and the other sides (so a furnace's result comes out whichever side was registered). Inventory access is per loader in `ItemPorts`: Fabric Transfer API, NeoForge `Capabilities.Item.BLOCK` (>=1.21.10) or `Capabilities.ItemHandler.BLOCK` (1.21.1), Forge `ForgeCapabilities.ITEM_HANDLER`.
- **Storage networks** (`logistics/HubNetworks`, `NetworkLink`, `NetworkStorage`, `logistics/compat/`): hubs have a block entity (`LogisticsHubBlockEntity`, no saved data) so they can be devices on Applied Energistics 2 and Refined Storage networks: a cable touching the hub joins it, and the network becomes an extra Inventories row (`ME Network` / `RS Network`, blank X/Y/Z so `matchRows` never matches it) usable in Transfers; Stock lists its `ServerConfig.hubNetworkStockRows` most common items. The compat classes are the only code that imports AE2/RS and are only loaded by `HubNetworks.init` when the mod is installed. Where a mod exists is set by `deps.ae2` / `deps.refinedstorage` (RS 2/3) / `deps.refinedstorage1` (RS 1, a Modrinth version id) in `stonecutter.properties.toml` (compile-only), which `stonecutter.gradle.kts` turns into the `ae2` / `rs` / `rs1` Stonecutter constants the compat files are wrapped in: AE2 on 1.20.1 (Fabric, Forge), 1.21.1, 26.1.2, 26.2 (NeoForge); RS 2/3 on 1.21.1 and 26.1.2 (Fabric, NeoForge); RS 1 on Forge 1.20.1. Cores (`Ae2HubLink`, `RsHubLink`, `Rs1HubLink`) are shared; small per-loader installers (`Ae2NeoForge`, `Ae2NeoForgeTransfer` for >=1.21.10, `Ae2Forge`, `Ae2Fabric`, `RsNeoForge`, `RsNeoForgeTransfer`, `RsFabric`) supply how the mod finds the hub and the loader's fluid type, so there are no nested Stonecutter blocks. AE2 before 1.21 only finds devices whose block entity implements its interface, so there `HubNetworks.setEntityFactory` makes `Ae2HubBlockEntity` instead. RS 1 needs its node type registered at setup (`HubNetworks.addSetup`, Forge common setup) and a Forge capability (`NetworkLink.capability`, passed through by the block entity); `NetworkLink.broken` (not chunk unloads) removes its node. Moves to/from a network go through `ItemPorts.moveWithNetwork` (simulate, then move a stack at a time).
- **Guide** (`guide/`): a step-by-step picture guide (`GuideScreen`), opened by the picker's Guide button, the Excel Guide book (`GuideBookItem`, `ClientHooks.openGuide`) or by holding W over an Excel item's tooltip (`ClientHooks.guideTooltip`, added by `GuideBlockItem`, `ExcelOnAStickItem` and `SharedWorkbookItem`). Its chapters, captions and frames are data in `assets/excelcomputer/guide/guide.json`; each frame's picture is `textures/gui/guide/<image>.png` (any size), and a missing picture shows its `shot` note instead.
- `ColorPalette` holds the UI and Excel color mappings.

## Versioning

Bump `mod.version` in `stonecutter.properties.toml`. Commit messages follow the pattern `1.0.x *short description of feature`.
